# 雨量证据补核与供水建议签发 v1（irrigation.rain_audit）

合作社月底核对田间水账时，有些日期的自动雨量记录只留下几个**可能值**；分段
雨量汇总表给出的区间总深度、土壤探头的日终储水闭区间，以及完整的实际灌溉记录
仍可查。本模块在完全保留现有日水账口径（`irrigation.balance.step` 的输水效率、
入渗上限、径流、容量渗漏、实际 ET、缺水与建议顺序）的前提下，先枚举**现有证据
允许的全部完整可能历史**（逐日雨量序列），再判断下一日的田间供水建议能否签发，
并在必要时给出一份单日追查单，说明值班员当班应先查哪天、查到不同数值后哪些
建议可以签发。

公开接口为 `irrigation.rain_audit.run(data)`，命令为
`soil-water-rain-audit --source INPUT --output REPORT`，二者共用同一业务逻辑，
仅用 Python >=3.11 标准库。全部水量与边界比较使用 `fractions.Fraction` 精确
有理数，不使用浮点或容差；**输入对象不会被修改**，非法数据抛 `ValueError`。
本模块只**复核历史记录与既有建议**：不重派已经发生的灌溉，也不下发任何设备
指令。`run`、`plan`、`meter_ledger`、`reuse_water`、`land_water` 与五个既有
命令的接口与行为保持不变。

## 1. 输入结构

输入根对象**恰好**包含 `fields`、`applications`、`weather`、`rain_windows`、
`probes`、`checkable_rain_dates` 六个键；任何未声明字段（含拼写错误）一律拒绝，
`weather`、`rain_windows`、`probes` 等新增对象同样不接受未声明字段。

- `fields`：沿用现有日水账的田块字段与校验（`id`、正整数 `area_m2`、
  `capacity_mm`、`infiltration_mm`、非负整数 `opening_mm`、`threshold_mm`、
  `target_mm`、1..1000 的 `efficiency_permille`，限值关系
  0≤threshold≤target≤capacity、opening≤capacity）。规模为 **1..4** 个田块，
  整个窗口采用同一组田块，**不做田块拆并**。
- `applications`：沿用现有日水账的 `field_id`、`date`、`gross_mm` 与校验
  （非负整数毛供水，每个田块日最多一条，引用未知田块或气象窗口外日期失败）；
  未出现的田块日按 **0** 计。整个窗口的实际毛供水是给定的。
- `weather`：按日期**升序且严格连续**的 1..31 个气象日，每行**恰好**含
  `date`、已知的 `et_mm` 和 `rain_mm_choices`。`rain_mm_choices` 是 1..3 个
  **互不重复**的非负整数候选，不要求有序（内部按升序使用）；只有一个候选即
  代表已知雨量。**最多九天**可以有多个候选。每天全体田块采用同一个候选雨量，
  不按田块分别猜测。
- `rain_windows`：每条**恰好**含 `from_date`、`through_date`、`total_rain_mm`，
  表示当地雨量汇总表上该**闭区间**内的精确总深度（非负整数）。起止均须是窗口
  内日期，起日不晚于末日；同一起止组合至多一条。区间可以重叠或嵌套，每一条都
  必须满足。
- `probes`：每条**恰好**含 `field_id`、`date`、`min_closing_mm`、
  `max_closing_mm`，表示探头和维护记录给出的日终储水闭区间。同一田块日最多
  一条，只测试当天 ET 扣除后的土壤储水。上/下界使用**精确的规范整数或分数字
  符串**（例如 `"0"`、`"3/2"`），满足 0 ≤ 下界 ≤ 上界 ≤ 该田块容量。
- `checkable_rain_dates`：可以查回准确原始雨量的日期数组，日期须在气象窗口内
  且不重复。空数组表示当班无可追查的档案；**不因某日可追查而假设已知其实际
  雨量**。

日期、田块身份、整数和已有对象字段的兼容口径沿用原规则（`type is int`，bool
一律拒绝；字符串身份保留原值）。除按日期输入的 `weather` 外，其余输入数组及
候选值的排列不影响业务结果。

## 2. 完整可能历史

一份**完整的可能历史**对应一条逐日雨量序列：每天取一个候选，使所有分段汇总
成立；从每个田块原有期初值开始，用该序列和固定的实灌量按现有田间水量平衡顺序
（`balance.step`）逐日核算，且所有日终探头界限都成立。必须延续**真实的上日
结存**，不能把探头上、下界当作新期初来调水账。天气分段与多田块探头约束
**同一条**历史，不能拼接分别过关的日期或田块。

两条雨量序列即使最后落到相同储水、甚至得到完全相同的签发，也仍是**两条不同的
历史**。较晚的证据可以排除早期某个曾经可能的值。

所有数值及边界比较使用精确口径；供水建议按现有阈值、目标水深、输水效率与向上
取整规则（`balance.step` 的 `advised_next_gross_mm`）计算。

## 3. 报告（schema_version = 1）

### 3.1 无可能历史

结构合法却不存在可能历史时，返回 `status="inconsistent"`、`history_count=0`
和非空中文 `reason`，CLI 正常退出 0；**不输出任何**水账范围、建议或追查安排。

### 3.2 存在可能历史

返回 `status="consistent"`、精确整数 `history_count` 和以下内容：

- `rain_daily`：按日列出 `date` 和 `possible_rain_mm`——完整可能历史在当日
  真正取过的雨量整数，去重升序。
- `field_daily`：按日期、田块列出 `date`、`field_id` 和 `closing_mm`、
  `unmet_et_mm`、`runoff_mm`、`drainage_mm` 四项实际可能范围，各用含 `min`、
  `max` 的对象表示，端点是规范有理数字符串。端点从**完整历史**取值，只承诺
  每项的最小和最大，不承诺范围内任意值都可得或各项端点能同时出现。
- `next_advice`：按田块列出 `field_id`、`possible_gross_mm` 和
  `released_gross_mm`。用末日水账的 `advised_next_gross_mm` 汇出不同可能
  整数，去重升序。**仅当所有可能历史给出同一个整数**才签发这个值；零也是可
  签发的明确建议。只要可能值不唯一就留待核，`released_gross_mm` 为 `null`。
  储水范围不唯一时，建议仍可能一致。这里签发的是按现行规则得出的次日建议，
  不代表已承诺用水。
- `follow_up`：`null` 或一份**单日**追查单。对每个可追查且仍有多个实际可能
  值的日期，分别以“查回的准确雨量等于某个可能值”为条件，只用与该结果相容的
  完整历史重新计算 `next_advice`。已能签发的建议不会因增加证据被撤回。
  1. 先排除那些**无论查到哪个值都无法多签发任何田块**的日期；
  2. 其余日期按**最坏情况下**待签发田块数最少优先，再按**最好情况下**待签发
     田块数最少优先，仍相等取**最早**日期。
  如果当前无待签发田块，或无可改善的日期，则填 `null`。
  选中的对象含 `date`、`worst_withheld_count`、`best_withheld_count` 和
  `outcomes`；`outcomes` 按雨量升序，每项含整数 `rain_mm`、该条件下的
  `history_count` 和齐全的 `next_advice`（格式同总表）。不为不可能的值出
  分支，不假设哪种结果更常见，也不把几天的追查结果合在一张单里。

重新提交已查回的原始值时，可将相应日期的候选替换成这个单值；对于原先真实可能
的值，新报告的 `history_count` 与建议须与追查单的对应分支一致。

## 4. 失败与文件行为

命令沿用既有严格 JSON 读取（重复键、`NaN`/`Infinity` 一律拒绝）与“全部计算
完成后原子新建报告”的约定：成功退出 0（包括 `status="inconsistent"`）；
输入或文件错误退出 2 并给出可读错误；目标已存在时保留原文件、绝不覆盖、不发布
半份报告。

## 5. 边界

本模块是对历史雨量证据与既有建议的离线复核，不重派已经发生的灌溉、不选择新的
供水计划、不预测未来天气、不操作设备，也不读写计量台账或回用水台账。mm×m²=升，
无隐式单位换算。ET 是调用者给定值。
